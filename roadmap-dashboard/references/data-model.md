# Data model (`.claude/roadmap/`)

All files are JSON with `"schema": 1`; RM writes them. Read them through `RM status` and `RM show`, not by opening them.

## plan.json (active phases, with all their features and stories)
`{schema, project, generated, phases, features, stories, agents, counts}`
- `phases[]`: `{id, name}` (ids `m1...`). `features[]`: `{id, phase, name, points?, estTokens?}` (`f...`). `points` is one of the Fibonacci scale `1,2,3,5,8,13,21`; `estTokens` is a non-negative integer. Both are optional, set with `RM set-feature <feature> [--points N] [--estTokens N]` (an empty string clears the field), validated by `RM validate`, and survive archive and reopen.
- `stories[]`: `{id, feature, name, status, agent?, critic?, loop?, escalated?, completed?, obe?, outcome?, details?}` (`s...`). `status` is one of not-started, planning, plan-review, progress (Implementing), review, approval, done. `loop` is like `"1 / 2"`; `escalated` like `"Sonnet -> Opus"`. `details` = `{desc, criteria:[{t, done}], log:[{when, what}], notes}`; it is dropped when the story closes.
- `agents{}`: chips only, `{id: {name, initials, model a|b|c, modelLabel, role}}`, shown on story cards. There is no roster or agent status.
- `counts`: computed (`overall`, `archivedPhases`, per-phase done/total; totals include archived stories). Never hand-edit.

## plan-archive.json
`{schema, phases, features, stories}`: only whole finished phases with their features and stories, moved by `sweep` (never a phase with a story-less feature); `add-feature` or `reopen-phase` moves one back. The Archive view fetches it lazily. Detail logs of closed stories live in `archive/story-logs.jsonl` (never loaded).

## Archive tab behaviour
Features are never archived on their own: a done feature stays in `plan.json` and the Plan tab shows it minimized. Only a phase whose stories are all done is archived, as one card nesting its features, in the Archive view (grouped by completion month, searchable). Side work goes into ONE phase named "Side track": add a feature to it (`add-feature --phase P` reopens it if archived); `add-phase` refuses a second "Side track" phase. Progress counts and the ring still include archived work. A phase with no stories never counts as done. Closed stories carry a `completed` date (`close-story` sets it).

## Story types
A story is `story` by default (no field stored) or `bug` (`"type": "bug"`), set with `add-story --type bug` or `set-story S --type bug`. Bugs go through the same pipeline; the type only labels them (a BUG chip in the Plan, Tree and Archive views) so defects can be told from planned work. The type is kept when a story is archived.

## Closed without being built (OBE)
`close-story --obe` marks a story overtaken by events. It counts as done and shows an OBE chip; say why in `--outcome`. Use sparingly: it makes progress look better than the work delivered.

## tokens.json
`{schema, generated, total, totals, unattributed, unmapped, stories, features, phases}`. `total` is fresh tokens (input + cache write + output). `totals` has fresh, input, cache_write, cache_read, output, requests, seconds, `orch_fresh`, `sub_fresh`, models. Each of `stories`, `features`, `phases` maps an id to the same fields. Phases plus unattributed plus unmapped equals the total. `RM tokens` (or `refresh`) rebuilds it from the session transcripts using `ledger/events.jsonl` (which story was active when) and Agent descriptions tagged `[story/role]`; `ledger/attribution.json` maps untagged subagents by agentId.

## activity.json
`{schema, generated, window:{days, since}, buckets, features, recent, tree}`, written by `RM activity` (also run by `RM refresh`). `buckets[]`: `{date, stories, features}`, one per day in the window. `features[]`: `{id, name, phase, phaseName, points, estTokens, completed}`, recently finished features. `recent[]`: `{date, kind, id, name, feature?, phase, phaseName, agents, obe?}`, capped and newest first. `phaseName` is resolved when the file is built, because an archived phase's name lives only in `plan-archive.json`, which these tabs deliberately never load. `tree[]`: `{id, name, completed, features:[{id, name, completed, points, stories:[{id, name, completed}]}]}`, the full phase > feature > story completion tree. Config keys in `ledger/config.json`: `activity_days` (default 30) and `activity_max_recent` (default 100). It deliberately carries no token totals — `tokens.json` already has them per story, feature and phase, so the Activity and Tree tabs look them up client-side instead of duplicating them.

## map.json, git.json
`map.json`: `{schema, generated, project, districts, nodes, relations}` (Project map tab). `git.json` (schema 2): `{schema, generated, days, since, head, branches, commits, events, totals, window_commits, lanes, max_commits, active}` (Git tab, last N days, newest first in topological order, at most `max_commits` in-window commits; `--max` or `git_max_commits`, default 150; `window_commits` is how many commits the window holds in all). The window is read without git's `--since` (which stops early on out-of-order dates and can lose the merge of an old branch) and filtered on commit date. Each commit: `{id, sha, short, ts, author, subject, parents, edges, lane, branch?, refs, files, ins, del}`; `branch` is the branch the commit belongs to (long-lived branches claim their first-parent chain first, then feature branches, then deleted branches named from their merge subject; absent when unknown) and the page prints it beside the graph; `id` is the first 8 hex chars of the sha, `parents` are parent ids, `edges` is `[[parentId, edgeLane], ...]`, `lane` the commit column, `lanes` the max lane count (parents outside the window are stubs). Lanes are the commit graph as `git log --graph` shows it: `assign_lanes` gives a first parent its child's lane and every other parent a lane of its own, so a linear stack of branches is ONE lane. Branch names are worked out over every commit of the window before the cap is applied.
`active` = `{base, days, branches:[...]}`, the Git tab's Active branches section. Each branch: `{name, head, tip, ts, local, remote, base, kind (feature|base), merged, merged_into[], ahead?, behind?, own?, stack?, same_tip?, pr?:{n, state open|merged}, links:[{s, n, f, via, why}], features:[{id, n, via, why}], more?}`. `via` is `subject`, `ledger`, `name` or `plan` (priority order) and `why` is the short text of the tooltip; `own` is the number of commits only this branch has, `stack` the nearest unmerged branch it is built on, `more` the story links beyond the 10 stored. Active = not merged into main/master/dev/phase-*, or a tip committed on within `days` days. Optional `branch` on a plan.json feature (string or list) is read as the lowest-priority link. `ledger/config.json` `git_prs: false` turns the `gh pr list` call off.

## ledger/
- `events.jsonl`: one row per status change `{ts, story, state, note?, agent?}`. `agent` is written by `set-status` / `start` / `event` (the `--critic` value for plan-review and review, else `--agent`); older events have none.
- `config.json`: `agent_effort` (agent type to effort), `orchestrator_effort`, `idle_cap_seconds`, `git_days`, `git_max_commits`.
- `runs.jsonl`: per-request token rows. `RM tokens` rebuilds rows only for sessions whose transcript still exists and keeps the old rows of sessions whose transcript was deleted (retention), so it is also the only copy of that spend; do not delete it. `attribution.json`: see above.
- `published.json`: `{url, at, files:{name: sha256}}`, written by `mark-published`.

## commands.json
Project-owned data for the optional Commands tab (`add-tab --id commands --title Commands --script tab-commands.js --data commands=commands.json`): `{schema, intro, groups:[{id, name, blurb, commands:[{label, note, prompt}]}]}`. Each command renders a button that sends its `prompt` to the Claude session watching the page (comments capability) or copies it when no session is reachable. The tab loads only this small file.

## tabs.json
`{title, subtitle, tabs:[{id, title, script, data:{key:file}, lazy:{key:file}}]}`; project-owned. The order of `tabs` is the order of the tab bar (Plan, Execution flow, Git activity, project tabs, Project map last); nothing in the code fixes it. Add a tab with `RM add-tab`. The script, `data` and `lazy` files of every listed tab are published with the page. Keep the `data` files small (only what the first view draws) and put descriptive detail in a `lazy` file the script fetches with `ctx.load(name)` on first selection, so the tab opens cheaply.

## flow.json
`{schema, generated, days, since, max_events, lanes, features, stories, rows}`, written by `RM flow` (also by `RM refresh`), read from the ledger only. `rows[]` newest first: `{ts, story, state, loop?, agent?, asrc?, chg?, tok?}` (`asrc` = where `agent` came from: `event`, `run` or `story`; the order is event, then run, then the story record's agent/critic when `run_stage(name)` equals the state; orchestrator/claude are never filled; a collapsed repeat keeps the latest agent) (one row per status step; back-to-back repeats collapsed; `loop` is the 2nd, 3rd... visit of a stage in one cycle; `agent` is the subagent type from `runs.jsonl` when a run of that story and stage overlaps; `chg` = 1 when that agent differs from the stage's earlier one; `tok` = fresh tokens (input + cache write + output) of the runs attributed to the step, absent when none: each run goes to the one step of its story with the same stage whose span holds the run's start, a range like `s114-s116` in the description is split evenly, orchestrator runs are skipped). `stories{id: {name, feature, lane, cut?, tokm?, toku?, unattr?}}` (`tokm`/`toku` = fresh tokens of the story's subagent runs matched / not matched to a step; `unattr` = reason text, present when the story has spend but no step shows tokens; `run_stories` reads every story id in a description, up to 12): `lane` 1.. (the main line is lane 0), lanes are shared only by stories that do not overlap (an unclosed story keeps its lane up to the newest row), `cut` marks a story whose earlier history is outside the window. `features[]`: `{id, name, phase}` in order of first appearance; `phases[]`: `{id, name, short}` for those features' phases (`short` is the Phase column label). Capped by `flow_days` (14) and `flow_max_events` (250) in `ledger/config.json`. Lazy: `tabs.json` lists it under the Execution flow tab's `lazy` (`flow` key), so it is fetched only when that tab opens.
